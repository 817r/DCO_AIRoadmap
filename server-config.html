How the config works

A folder in the server profile, read once at startup. Nothing is read while the server runs, so edits made during a session are lost at the next write.

FileHolds
Core.jsonGeneral settings, performance, Game Master permissions, logging.
Soldiers.jsonSkill, aim, perception, suppression, dodge, grenades, personality, night, aggression, voice.
Squads.jsonIdle, stragglers, CQB, behaviour, contact sharing and reports, medics, break contact, squad jobs.
Commander.jsonCommander spawner, doctrine, group presets, commander tactics.
Vehicles.jsonVehicle AI.
Advanced/<group>.jsonEvery tune_ key, one file per group — tune_hear_shot_err lives in Advanced/hear.json.
Factions/<FACTION>.jsonValues for one faction only.
A key in the wrong file still works. It is logged as cfg_key_wrong_file and moved to its home file at the next rewrite. One broken file is ignored on its own — the rest still apply, and the broken one is never overwritten.

First start

  1. Start the server once with DCO_AI loaded.It writes $profile:DCO/Config/ with every setting at its current value, one key per line, split across the files above.
  2. Stop the server, edit the keys you care about, start it again.The log line N settings overridden from ... tells you how many were applied — check it matches what you changed.
  3. Keep only what you changed, if you prefer a short file.Missing keys are filled back in at the next start, so a four-line file works exactly like a full one.
Never edit a running server. The config is read at startup, and a later write from the game overwrites your file. Stop it first.
Upgrading from the single-file config? If only the old $profile:DCO/DCO_GlobalConfig.json exists, it is read once, split into the folder with every value kept — a factions block becomes Factions/<FACTION>.json — and renamed to .migrated.bak. Logged as cfg_split_migrated. That is also why the templates below still work as a single file.
Whole numbers are fine. "aiAggression": 2 and 2.0 both work. Quotes around a number do not — that's a cfg_bad_type.

Rewrites and migration

WhatWhenEffect
Auto generateOnMissing keys are added with the current value, and the old file is copied to .bak first. Turn it off to drop a key for good — otherwise deleted keys come back.
Default migrationOn updateA key still sitting at the old shipped default takes the new one, logged as cfg_default_migrated. Values you edited are never touched.
Defaults recordPer worldDCO_GlobalConfig.defaults.<world>.txt records every default for that world, so rotating scenarios doesn't trigger migrations. Don't edit these.
Save from Game MasterOpt-ingmSaveConfig decides who may press Save to server config: gm, admin (default) or off. It writes every current value, defaults included.
Misspelled keysDroppedOnly real keys survive a rewrite, so a typo quietly disappears. Copy names from the reference below.

When something's wrong

The server never refuses to start over a config problem — it logs and carries on. Grep dco.log for these:

Log lineMeans
cfg_clampedValue outside its range; it was pulled to the nearest limit.
cfg_bad_typeWrong type — a quoted number, or a decimal where a whole number is required. That key keeps its old value and the file is not rewritten.
cfg_parse_failThat one file is broken. It is ignored and never overwritten; the other files still apply and its keys fall back to their defaults.
cfg_key_wrong_fileA real key in the wrong file. It still works and is moved at the next rewrite.
cfg_split_migratedAn old single-file config was split into the folder.
cfg_unusedA key nothing reads — almost always a misspelling.
cfg_faction_unknown_keyA key inside a factions block that DCO doesn't know.
cfg_faction_global_onlyA key that only works server-wide, ignored inside a faction block.

Templates

Four starting points. Each changes only a handful of keys; everything else is filled in with the shipped default at the next start, so you can drop one in as-is. Download it, back up whatever was there, save it as $profile:DCO/DCO_GlobalConfig.json and restart — DCO splits it into the config folder for you. Already on the folder layout? Paste the keys into the matching file instead.

Performance

For a large PvE server where frame time matters more than the last few percent of behaviour. LOD keeps commander groups fighting at distance without full simulation, and contact reporting is the other big recurring cost.

{
  "_comment": "DCO AI - Performance. For a big PvE server where frame time matters more than the last 5% of behaviour. Turn perfProfiling on for one session to measure, then off. DCO AI template. Rename to DCO_GlobalConfig.json and put it where your server keeps that file (back up the old one first). Only the keys below change; everything else is filled in with the shipped default at the next start. Delete the file to go back to defaults.",
  "lodMode": 1,
  "perfProfiling": false,
  "contactReportMaxPerScan": 2,
  "contactReportScanInterval": 25
}
Measure, don't guess. Set perfProfiling to true for one session: every 30 s it writes FPS, AI count by LOD, time per DCO system and queries per second to perf.log, and lists which systems ran on any frame over 50 ms. Turn it off afterwards.

Per faction

One faction gets its own values on top of the global ones — a trained army against a militia in the same mission. Any key from the reference works. On the folder layout each faction is its own file, Config/Factions/USSR.json, holding just that faction's keys; in the single-file template below they sit in a factions block and are split out on first start.

presets/factions.jsonDownload
{
  "_comment": "DCO AI - Asymmetric factions. Global values apply to everyone; the factions block overrides them per faction. Layer order, last wins: global file, GM global, this faction block, GM faction. DCO AI template. Rename to DCO_GlobalConfig.json and put it where your server keeps that file (back up the old one first). Only the keys below change; everything else is filled in with the shipped default at the next start. Delete the file to go back to defaults.",
  "aiSkillDefault": 2,
  "aiAggression": 1,
  "factions": {
    "US": {
      "aiSkillDefault": 3,
      "aimAccuracy": 1.2,
      "aiAggression": 1.2
    },
    "USSR": {
      "aiSkillDefault": 2,
      "aiAggression": 1
    },
    "FIA": {
      "aiSkillDefault": 1,
      "aiAggression": 1.6,
      "takeCoverChance": 0.5,
      "personalityWeightReckless": 20
    }
  }
}

Layer order

Four layers, last one wins: 1. global values in this file → 2. Game Master global settings → 3. this file's faction block → 4. Game Master faction settings.

Some keys are server-wide only and are ignored inside a faction block: the doctrine* keys, the groupPreset* keys, gmSaveConfig, startupPresetPrompt and perfProfiling. A faction that doesn't exist in the mission, or an empty entry, is skipped and left in the file.
Edit the block while the server is stopped. A Game Master save writes the faction block as it was when the server started, so live edits to the file get overwritten.

The aggression trap

Read this before touching soldier settings. aiAggression is not an independent slider — it rescales several others, and the shipped value already sits in the range where it does.

RuleEffect at the shipped value
Effective aggressionaiAggression × 2.5. Shipped 1 means an effective 2.5.
takeCoverChance
dodgeChance
suppressionEffect		Multiplied by 1 / effective whenever that is above 1 — so ×0.4 as shipped. A takeCoverChance of 0.8 is a real 0.32. They still work across their whole range, just lower than the number suggests.
grenadeUsage
glUsage		Multiplied by effective aggression and capped at 1. At the shipped value everything from 0.4 to 1.0 behaves identically — only values below 0.4 change anything.
Squad pull-backCasualty thresholds scale with aggression too. At the shipped value squads almost never fall back on losses alone.

What was actually measured

From stress runs of roughly 170 AI, one run per value — indicative, not a benchmark.

KeyTestedResult
aiAggression0.5 / 1 / 3First kill at 189 / 176 / 127 s, panic flights 53 / 18 / 2. Low is careful and easily shaken; high pushes in fast and rarely panics. Above 1 the squad posture choice stops changing, but soldier-level effects keep growing.
suppressionEffect0.2 vs 1.0Panic flights 1 vs 23, deaths while panicking 0 vs 17. The strongest single lever on whether AI can be pinned at all.
takeCoverChance0.2 vs 0.8Barely moved — 76 vs 74 deaths. Small effect at the shipped aggression, which is the rescaling above in action.
superiorRatio1.0 vs 2.0No clear effect in a test without commanders. It mainly changes when commanders and groups decide to attack.
Practical order. Set aiAggression first, play a round, and only then adjust cover, dodge and suppression — their effective values all move when you change it.

Tuning keys

Beyond the named keys there are 535 tuning keys, all prefixed tune_. They're the numbers the AI reasons with — hearing error, cover scoring, flank geometry, morale thresholds — exposed rather than buried. A value equal to the default means the built-in behaviour, so a file that mentions none of them behaves exactly as shipped.

Naming

Each key has two spellings, and both are accepted everywhere — config, Game Master and API: the config name tune_hear_shot_err, or the short internal name hear.shot_err. The generated DCO_GlobalConfig_README.txt next to your config file lists every key with its default and range.

Change these one at a time. They were built to be tuned against a measurement, not guessed at. Many are flagged experimental in the Game Master settings window because they're still being validated — if a run gets worse, delete the key rather than compensating with a second one.

Troubleshooting

SymptomCheck
My edits did nothingLook for N settings overridden from ... at startup. If N is 0, the file is somewhere else — it has to be $profile:DCO/DCO_GlobalConfig.json under the -profile folder the server actually uses.
A key vanished from the fileIt was misspelled. Only real keys survive a rewrite — copy the name from the reference above.
My value went back to the defaultEither it was clamped (cfg_clamped), or it was still sitting at the old shipped default and got migrated (cfg_default_migrated). Values you edited are never migrated.
The whole file was ignoredcfg_parse_fail — a trailing comma or a missing brace. The previous values stay and nothing is written, so your file is still intact.
Faction values ignoredcfg_faction_global_only for server-wide keys, cfg_faction_skip for a faction that isn't in the mission, cfg_factions_not_object if the block is an array rather than an object.
Game Master changes gone after restartGame Master edits apply live but aren't written back unless somebody saves. gmSaveConfig controls who may.
Cover and suppression feel weaker than the numbersThey are. See the aggression trap.
Lower isn't better, or vice versaCheck the shipped value in the table rather than your intuition. Several keys ship above 1 (aiPerception 1.5) and several below (takeCoverChance 0.8).
